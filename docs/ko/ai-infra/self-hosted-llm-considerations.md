# 리전 선택 고려사항

대규모 GPU 학습/추론 인프라를 **자체 호스팅(Self-managed)** 환경으로 구축할 때, 리전과 AZ 선택은 단순한 위치 결정이 아니라 **학습 성능·비용·일정 전체에 영향을 주는 설계 결정** 입니다. 같은 인스턴스라도 리전·AZ에 따라 확보 가능한 용량, 스토리지 성능, 네트워크 구성, 지원 서비스가 달라지기 때문입니다.

이 페이지는 "어떤 점을 미리 주의해야 하는가"를 이해하는 데 목적이 있습니다. 각 항목의 **구체적인 제약 수치·리전별 현황·해결 방안은 환경에 따라 크게 달라지므로**, 실제 설계 시에는 담당 GTM SSA와의 논의를 통해 확정하시기를 권장합니다.

!!! tip "이 페이지의 사용법"
    아래 고려 영역은 **"무엇을 점검해야 하는지"의 체크포인트** 입니다. 각 항목이 실제로 어떤 제약으로 나타나고 어떻게 해결하는지는 워크로드·모델·일정·리전 조합에 따라 달라지므로, 구체적인 설계와 수치는 담당 GTM SSA와 함께 검토하십시오(아래 [논의 안내](#논의-안내) 참고).

## 1. 먼저 명확히 할 것 — 워크로드 요구사항

리전을 논하기 전에, 다음이 정의되어야 합니다. 이것들이 리전·인스턴스·스토리지 선택 전반을 좌우합니다.

- **워크로드 성격**: 학습(사전학습 / 파인튜닝 / 재학습)인지 추론(온라인 / 오프라인 / 배치)인지
- **모델 특성**: 아키텍처(Dense / MoE / Open-weight), 학습 범위, 파라미터 규모(MoE는 활성 파라미터 포함)
- **데이터 주권·보안**: PII 포함 여부, 데이터 국외 이전 가능 여부, 특정 AZ·이중화 요구
- **성능·운영 요구**: 스토리지 용량·대역폭, 네트워크 성능, DR, MLOps 수준

!!! note "데이터 주권이 리전을 먼저 결정하기도 합니다"
    규제 산업이나 민감 데이터를 다루는 경우, 데이터가 특정 국가를 벗어날 수 없어 리전 선택지가 사실상 제한될 수 있습니다. 이때는 성능보다 데이터 주권이 우선 제약이 됩니다. 구체적 적용 가능 여부는 컴플라이언스 검토가 필요합니다.

## 2. 구축 방식에 따라 고려사항이 달라집니다

자체 호스팅은 여러 방식으로 구축할 수 있고, 선택에 따라 리전·AZ·용량 전략이 달라집니다.

- **Amazon EC2** — 직접 구성하거나 자체 플랫폼을 보유한 경우
- **AWS ParallelCluster / PCS** — 인프라 관리와 Slurm 스케줄링을 자동화
- **Amazon EKS** — Kubernetes로 학습·추론을 통합 운영
- **Amazon SageMaker HyperPod** — 완전 관리형 플랫폼

각 방식은 리전별 지원 현황과 운영 역량 요구가 다릅니다. 어떤 방식이 적합한지는 [AI 인프라 의사결정 가이드](infra-decision-guide.md)를 참고하시고, 구체적인 리전 적합성은 담당 GTM SSA와 논의하십시오.

## 3. 리전 선택이 AI 워크로드에 미치는 영향

리전·AZ 선택이 왜 중요한지를, 실제로 학습·추론에 어떤 영향을 주는지 관점에서 정리합니다. **아래는 "이런 제약이 존재할 수 있다"는 인식을 위한 것이며, 구체적인 수치와 현재 지원 현황은 수시로 바뀌므로 담당 GTM SSA와 확인이 필요합니다.**

### 컴퓨팅 — 인스턴스 세대와 가용성

- 최신 세대 GPU 인스턴스는 **모든 리전에 동시에 제공되지 않습니다.** 원하는 인스턴스가 대상 리전에 있는지, 필요한 수량을 확보할 수 있는지가 일정과 직결됩니다.
- 세대에 따라 메모리·연산 성능·지원 데이터 타입(FP8/FP4 등)이 크게 다릅니다. **워크로드가 요구하는 정밀도·메모리를 어떤 인스턴스가 충족하는지** 가 선택의 핵심이며, 실제 성능은 모델·구성에 따라 달라져 사전 검증(PoC)이 필요합니다.

> **왜 중요한가**: 인스턴스 세대를 잘못 고르면 메모리 부족으로 모델이 안 올라가거나, 반대로 과잉 사양으로 비용이 낭비됩니다. 세대 간 성능 차이가 학습 기간과 비용을 좌우합니다.

### 스토리지 — 처리량이 GPU 활용률을 좌우합니다

- 고성능 공유 스토리지(예: FSx for Lustre)는 **배포 타입·리전·AZ에 따라 가용성과 성능 특성이 달라집니다.** 일부 환경에서는 처리량에 상한이 생기거나, 원하는 성능 등급이 특정 리전·AZ에서만 제공될 수 있습니다.
- AZ별로 확보 가능한 스토리지 용량이 다를 수 있어, 용량 사전 점검이 필요합니다.

> **왜 중요한가 (잘 간과되는 부분)**: 대규모 학습에서 **GPU는 데이터를 기다리며 멈춰 있을 수 있습니다.** 스토리지 처리량이 GPU의 데이터 소비 속도를 따라가지 못하면, 비싼 GPU가 유휴 상태가 되어 학습 시간과 비용이 함께 늘어납니다. 즉 스토리지 제약은 "저장"의 문제가 아니라 **"GPU 활용률과 비용"의 문제** 입니다. 그래서 리전·AZ의 스토리지 성능 가용성을 반드시 사전에 확인해야 합니다.

### 네트워킹 — 노드 간 통신이 분산 학습을 좌우합니다

- 멀티노드 분산 학습은 노드 간 고속 인터커넥트(EFA)에 의존하며, **인스턴스 세대에 따라 지원하는 EFA 세대가 다릅니다.**
- 노드 배치(물리적 근접성)가 통신 지연에 영향을 주며, 이는 리전·AZ·용량 확보 방식과 연결됩니다.

> **왜 중요한가**: 분산 학습에서 노드 간 통신은 전체 학습 속도의 병목이 될 수 있습니다. 통신 대역폭이 부족하거나 노드가 물리적으로 멀리 배치되면, GPU를 아무리 늘려도 통신 대기 때문에 성능이 선형으로 확장되지 않습니다. 네트워크 구성은 리전·AZ 선택 시점에 결정되는 경우가 많아 사후 변경이 어렵습니다.

### 운영 — MLOps / LLMOps

- 전통 ML과 LLM/Agent 워크로드는 모델 크기, 서빙 방식, 모니터링 지표, 비용 구조가 다릅니다. 운영 도구와 플랫폼 구성이 리전별 서비스 지원 현황에 영향을 받을 수 있습니다.

## 4. 용량 확보 전략

GPU 수요가 많을 때는 단일 AZ·단일 리전·단일 인스턴스 타입만으로 원하는 용량을 확보하지 못할 수 있습니다. 이 경우 다음을 고려합니다.

- **Multi-Region / Multi-AZ**: 요구사항(데이터 주권·레이턴시)이 허용하는 범위에서 용량을 분산
- **Multi-Instance Family**: 이기종 인스턴스 혼용

!!! warning "이기종 혼용은 신중해야 합니다"
    서로 다른 인스턴스 세대·타입을 하나의 학습 작업에 섞으면, CPU 아키텍처·네트워크 구성·스토리지 성능 차이로 인해 예상치 못한 성능 저하나 오류가 발생할 수 있습니다. 느린 쪽에 전체 성능이 맞춰지는 하향 평준화가 대표적입니다. 혼용이 불가피한 경우의 구성 방법은 담당 GTM SSA와 논의가 필요합니다.

## 5. Local Zone 활용 시

GPU 용량 확보를 위해 Local Zone을 고려할 수 있으나, 상위(Parent) 리전과 **지원 서비스·스토리지 성능에 차이** 가 있습니다. 일부 서비스는 Local Zone에서 직접 제공되지 않아, 아키텍처를 상위 리전과 연계해 설계해야 할 수 있습니다.

> **왜 중요한가**: Local Zone에서 당연히 될 거라 가정한 서비스가 지원되지 않으면, 설계를 되돌려야 하거나 추가 네트워크 구성이 필요해집니다. 어떤 서비스가 영향을 받는지는 사전에 확인해야 합니다.

## 6. 온프레미스에서 이전하는 경우

온프레미스(예: InfiniBand 기반) 환경에서 AWS로 이전할 때는, 네트워크·스토리지·스케줄러의 동작 방식 차이를 사전에 검토해야 합니다. 특히 노드 간 통신 특성이 달라, 기존 환경의 성능 가정이 그대로 적용되지 않을 수 있습니다.
